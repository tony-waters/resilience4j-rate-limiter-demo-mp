# rest-service tracks email-service's rate-limit state and skips calls pre-emptively

`email-service` reports its rate-limit budget (`RateLimit-Limit`/`RateLimit-Remaining`/`RateLimit-Reset`) on every `/notifications` response, not just on `429`s. `rest-service` remembers the last-seen `remaining`/`reset` in memory and, once it knows the budget is exhausted, skips calling `email-service` entirely until `reset` passes — recording `Skipped` rather than making a call it already knows will be rejected. The alternative was simpler: keep calling and let `email-service`'s `@RateLimiter` reject as it does today. We chose to track state instead because the whole point of returning the headers is to let a well-behaved client avoid pointless rejected calls, and this demo exists to show that resilience4j pattern working end-to-end. The state is in-memory only, scoped to the single `rest-service` instance (no replicas, no persistence) — acceptable because there is exactly one instance, per `docker-compose.yml`, and losing the remembered state on restart just costs one optimistic call that reseeds it.
